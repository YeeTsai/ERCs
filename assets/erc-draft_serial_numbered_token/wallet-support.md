# What a Wallet Needs to Support This Proposal

> This file accompanies the draft ERC "Serial-Numbered Fungible Tokens". Its content was the section "What a wallet needs to support this proposal" of the draft. Section names in quotation marks refer to sections of the draft.

A wallet that does not know this proposal can use a token that conforms to this proposal as an ERC-20 token as usual. Its shortcoming is that the balance it displays can include units that cannot be sent, which the user discovers only when a send fails. On failure, a contract that follows the recommendations reverts with the errors this proposal defines (see clauses 3 and 5 of "Transferable balance" and clause 3 of "Acceptance check"). A wallet that can decode these errors can tell the user how much can be transferred to this payee address, which slice of serials cannot be sent, or that the incoming transfer was refused by the payee (`ERCXXXXTransferRefused`); but the errors do not state the cause, for example which reason the units are frozen for, or whether they are restricted by the flow rule of a class instead, or why the payee refused. To support this proposal fully, a wallet needs to do the following. All of the queries involved can be made with read-only calls and need no indexer.

1. Detection. Query the identifier of the core interface with ERC-165, then the identifiers of the freezing extension and the classification extension, and the identifier of the acceptance check.
2. Displaying the balance. `balanceOf` is the total. When the token implements the freezing extension, call `frozenBalanceOf(account)` to get the amount of it that is frozen, and call `freezeReasonsOf(account)` and `freezeReasonInfo` to explain why it is frozen. The amounts under the individual reasons cannot be added up, because the same unit can be frozen for several reasons. When the token implements the classification extension, also call `classesOf(account)` to get the breakdown of the balance by class, and call `classInfo` for every non-zero class and display the name it returns. The description documents of reasons and classes are only a supplement: a wallet can use them to display longer descriptions, images and properties, but displaying the balance does not depend on them.
3. Sending. After the user enters the payee address, call `transferableBalanceOf(from, to)`, use it as the upper limit of the amount that can be sent, and validate the amount against it. To explain why some part cannot be sent: on a token that implements the freezing extension, the frozen amount comes from the previous step; on a token that implements the classification extension, call `classAllows` for every class in the breakdown to find the classes that are not allowed to be transferred to this address. The two parts can overlap: a frozen unit can also belong to a class that is not allowed, so their amounts cannot be added up. A wallet can display them separately and note that the two can overlap. To know how many units the two block together, the wallet has to call `frozenRunAt` and `classRunAt` for each slice of the holding, find the serials that are frozen or whose class is not allowed, and take their union. `balanceOf(from)` minus `transferableBalanceOf(from, to)`, minus the size of this union, leaves a difference that comes from restrictions the implementation defines itself and attaches to serials; the wallet can only report its amount. These queries have to be made against the state of the same block. The payee might also refuse the incoming transfer (see "Acceptance check"): when the token supports the acceptance check and the payee address has code, the wallet should simulate the transfer before sending; if it is refused, the wallet can try again with `transferSlices`, naming longer slices. Other restrictions that the implementation itself provides (for example the account's receive limit suggested in "The acceptance check and failed payments") can likewise be discovered by the wallet only through simulation.
4. Estimating gas. The cost of a transfer depends on the number of slices it moves, so a wallet should estimate each transaction individually and not use a fixed value.
5. Optionally, display the slices of the holding, using `sliceCount` and `sliceAt`. When the token implements the freezing extension, call `frozenRunAt` for each slice of the holding to mark the frozen parts of it. When the token implements the classification extension, call `classRunAt` for each slice of the holding to get the class of each part. A run can extend beyond the boundary of the holding's slice, and the wallet has to truncate it to that slice. These calls have to be read at the same block.
6. Optionally, let the user choose which units to send. Use the result of the previous step to exclude in advance the frozen parts and the parts whose class is not allowed to be transferred to the payee address (determined with `classAllows`). Sort the slices the user selected in ascending order of start and send them with a single `transferSlices` call. If any one of the serials is frozen, or its class is not allowed to be transferred to the payee address, the whole call reverts.
7. Optionally, offer consolidation. When `sliceCount` returns a large number of slices, the wallet can suggest that the user consolidate: use the result of step 5 to exclude the frozen parts, sort the slices of one class in ascending order of their start, and call `consolidateSlices`; when there are very many slices, use several transactions. A token can leave consolidation closed, or set further conditions for it, in which case the call reverts; the draft defines no function for querying these conditions, so the wallet should simulate the call first. After a consolidation the serials of these units have changed, and slices the wallet read earlier have to be read again. To translate an old serial into the serial the unit has now, call `consolidatedRunAt` repeatedly until it reports that the serial is not consolidated.
